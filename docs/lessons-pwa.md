# PWA開発で踏んだ罠と対策

書架(読書記録PWA)の開発で実際に遭遇し、原因を特定して解決したもの。
LIFE QUEST・召喚録など、同じ構成(React + esbuild + Firebase + GitHub Pages)の
アプリでも再び踏む可能性が高いため、一般化して記録する。

---

## 1. Service Workerで成果物を事前取得してはいけない

### 症状
コードを直してデプロイしても、端末では古い画面のまま。
キャッシュを消すと直るが、しばらくするとまた再発する。

### 原因
`bundle.js?v=N` をService Workerの precache に入れていた。

デプロイは複数ファイルを順に上げるため、`sw.js` と `index.html` が先に反映され、
`bundle.js` がまだ古い瞬間が生まれる。その瞬間に新しいService Workerが動き出し、
**古い中身を「v=N」という新しい名前でキャッシュに焼き付ける**。
以後どれだけ正しい `bundle.js` を上げても、端末はキャッシュを返し続ける。

### 対策
precache するのは `index.html` と `manifest.json` のみに留める。
成果物やフォントは「**実際に読み込めた時に保存する**」方式にする。
`?v=N` が変われば別URLになるので、更新時は必ず取り直される。

### 一般化
**デプロイの順序に依存する仕組みを作らない。**
複数ファイルが揃って初めて正しい状態になる設計は、途中の瞬間に壊れる。

## 2. `Number(null)` は `0` になる

### 症状
「未入力なら未設定にする」つもりの処理が、最小値を勝手に設定していた。
評価を付けずに登録すると、必ず星1つが付いた。

### 原因
```js
let rating = Math.round(Number(input.rating));   // Number(null) → 0
rating = Number.isFinite(rating) ? Math.min(5, Math.max(1, rating)) : null;
// isFinite(0) は true なので通過し、max(1, 0) で 1 になる
```

### 対策
`null` / `undefined` / 空文字を**数値変換の前に**弾く。

```js
if (input === null || input === undefined || input === "") return null;
```

### 一般化
- JavaScriptの暗黙の型変換は、意図した分岐をすり抜ける
  (`Number(null)===0`, `Number("")===0`, `Number([])===0`)
- **同じ正規化処理を2箇所に書かない**。片方だけ直して食い違う

## 3. 日付は `toISOString()` を使わない

UTCに変換されるため、日本時間では日付が1日ずれる。
ローカル日付を自前で組み立てる。

```js
const isoLocal = (d) =>
  `${d.getFullYear()}-${String(d.getMonth()+1).padStart(2,"0")}-${String(d.getDate()).padStart(2,"0")}`;
```

---

## 4. 1日に複数件あり得るものを単数で持たない

日別の記録を `{ finish: book }` と単数で設計したため、
同じ日に2冊読み終えると後の1冊で上書きされていた。

### 一般化
「普通は1件」と「必ず1件」は違う。**普通は1件のものは配列で持つ**。
後から配列に変えるのは、UIを含めて広範囲の修正になる。

## 5. Windowsの `findstr` は日本語を検索できない

コンソールがShift-JIS、ファイルがUTF-8のため、バイト列が一致しない。
**正しくビルドできていても永久にヒットしない**ため、
「デプロイされていない」と誤診断する原因になった。

### 対策
ビルド結果の確認には、**ASCII文字列の版数マーカー**を埋め込む。

```js
export const BUILD = "myapp-build-v26";   // ASCIIのみ
```

あわせて **版数を画面に表示する**。
「手元のビルド」「サーバー上」「端末で動いているもの」の3つを
見比べれば、どこで止まっているかが推測なしで確定する。

## 6. importし忘れは画面が真っ白になる

未定義の関数を呼んだ瞬間に描画が止まり、**アプリ全体が白紙**になる。
しかも「その関数に到達する条件のとき」だけ起きるので、
手元では再現せず、実データのある環境で初めて出ることがある。

### 対策
- **エラー境界**を置き、壊れた範囲だけを切り離す(他のタブは使える)
- import/export の対応を**テストで機械的に検証**する
  (全ファイルのimport文を走査し、その名前が実際にexportされているか確認)

## 7. Firestoreのオフライン永続化は複数タブ方式にする

`persistentSingleTabManager` は保存領域を1インスタンスが占有するため、
PWAとブラウザタブを同時に開いた場合や、**OSにPWAを強制終了された場合**に
占有権が残り、次回起動時にデータを読めなくなる。

`persistentMultipleTabManager` を使う。

あわせて、**読み込み中の画面から必ず脱出できるようにする**。
判定順の都合でエラー表示に到達せず、利用者が操作不能のまま
取り残される構造になっていた。数秒待っても終わらなければ
状況と再試行手段を出す。

## 8. GitHubのSecret scanningは公開前提のキーにも反応する

ブラウザで動くアプリのAPIキーは、仕組み上どうしても公開される。
検知されても慌てず、**キーに制限がかかっているか**を確認する。

- Firebase の `apiKey` … 秘密鍵ではない。守るのはFirestoreのセキュリティルール
- Google Books APIキー … リファラ制限(`https://<user>.github.io/*`)+ API制限をかける

制限済みなら Close(Won't fix)で良い。

## 横断する教訓

1. **確認方法そのものを疑う**。「反映されていない」と判断した根拠が
   間違っていたことが二度あった。診断手段は先に検証する
2. **推測で原因を断定しない**。コードを読めば5分で分かることを、
   推測で語って複数回の往復を無駄にした
3. **失敗しても利用者が詰まない設計にする**。
   真っ白・永久読み込み・操作不能は、不具合そのものより体験を損なう
4. **仕様変更はテストで固定する**。「1日1冊前提」「単数で十分」のような
   暗黙の前提は、テストに書いておかないと後で静かに壊れる
